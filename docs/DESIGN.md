# 개인 투자 비서 앱 — 제품/기술 설계안 v0.1

> 상태: **검토 완료, 방향 결정됨** (아래 0.5절). 구현은 Phase 0부터.
> 입력: `브레인스토밍 결과` 문서 (2026-08-19)
> 이 문서는 "무엇을 만들지"가 아니라 **"어떤 구조로 만들지"** 를 다룬다.

---

## 0. 이 설계안의 한 문장 요약

> **뉴스를 저장하는 앱이 아니라, 사건(Event)을 저장하는 앱으로 만든다.**
> 뉴스는 사건을 만들기 위한 원재료이고, 화면에 보이는 모든 것(24시간/7일/30일 요약, 사건 기록장, 알림, 실적 발표 후 결과)은 **하나의 사건 테이블에 대한 서로 다른 질의**다.

이 결정 하나가 다음을 동시에 해결한다.

| 기획 요구 | 사건 중심 설계에서의 해법 |
|---|---|
| 24h / 7d / 30d 요약 (2장) | 기간별로 AI를 다시 돌리지 않고 **사건 테이블을 기간 필터링**. AI 비용이 3배가 아니라 1배 |
| 신규 사건 vs 후속 보도 구분 (3장) | 새 기사 클러스터를 **기존 사건과 매칭**. 매칭되면 후속, 안 되면 신규 |
| 중복 제거 (3장) | 사건에 기사가 N:1로 매달림. 중복은 구조적으로 사라짐 |
| 사건 기록장 (6장) | 사건 테이블을 시간순 정렬한 것, 그 자체 |
| 예정 이벤트 → 실제 발생 → 최근 사건 → 기록 (17장) | 예정 이벤트가 **사건으로 승격(promote)** 되는 상태 전이 |
| "특별한 일 없음" (5장) | 기간 내 중요도 임계값 초과 사건 개수 = 0 → 명시적 상태 |
| 알림 (18장) | 사건 생성 시점에 중요도 기준으로 트리거. 기사 단위가 아니라 사건 단위라 자연히 조용해짐 |

반대로, 만약 "기사"를 1급 객체로 두고 매번 요약을 생성하는 구조로 만들면 위 7가지가 전부 따로 구현해야 하는 별개 기능이 된다. **이게 이 설계의 핵심이다.**

## 0.5. 결정 사항 (2026-08-19)

| 분기점 | 결정 | 파급 효과 |
|---|---|---|
| 데스크탑 스택 | **보류.** 화면 없이 CLI(Phase 0)부터 | UI 스택 선택을 파이프라인 검증 이후로 미룬다. 좋은 판단 — 이 앱의 리스크는 UI가 아니라 "뉴스 30개 → 사건 3개"가 되느냐다 |
| LLM 예산 | **mock이 기본. 유료는 선택** (0.6절) | Phase 0 전체를 비용 0으로 돌린다. 토큰·비용 계측은 유지하되, 유료 전환은 구조 검증이 끝난 뒤 |
| 백그라운드 수집 | **작업 스케줄러 병행** | 수집기를 처음부터 독립 실행 진입점으로 만든다 |
| 배포 가능성 | **있음 → 공용/개인 2층 분리** | 사건 생성 코드는 "사용자"라는 개념을 몰라야 한다 |

### 네 결정이 하나로 수렴한다

따로 보면 별개 선택 같지만, 실제로는 **같은 것 하나**를 가리킨다.

```
Phase 0의 CLI  ==  작업 스케줄러가 실행할 헤드리스 수집기
               ==  나중에 서버로 올라갈 공용 층
```

즉 지금 만들 CLI는 버리는 프로토타입이 아니라 **이 앱의 최종 백엔드 그 자체**다. Phase 1에서 UI를 붙일 때 이 코드는 그대로 남고, 배포로 갈 때도 그대로 서버에 올라간다. 그래서 Phase 0을 "실험용"이 아니라 **제대로 된 코드로** 쓰는 게 맞다.

여기서 따라 나오는 제약:

- **UI를 몰라야 한다** — 출력은 stdout이 아니라 SQLite. CLI 출력은 사람이 보기 위한 부산물
- **사용자를 몰라야 한다** — `events` 테이블에 `user_id`가 없다. 관심자산 목록·알림 설정·읽음 상태는 별도 층
- **한 번 실행하고 끝나야 한다** — 상주 프로세스가 아니라 `collect --once` 형태. 스케줄러가 부르는 방식과 동일
- **놓친 실행을 따라잡아야 한다** — 마지막 성공 시각을 보고 그 이후 구간을 채운다

## 0.6. 비용 정책 — 무료가 기본, 유료는 선택 (2026-08-19 추가)

> **어떤 실행도 실수로 돈을 쓸 수 없어야 한다.** 돈을 쓰는 것은 켜야만 되는 기능이다.

이 앱은 연습용 프로토타입으로 시작한다. 그래서 "구조가 되는가"를 검증하는 단계에서
유료 API·금융 데이터 구독·서버가 **필수 구성요소여서는 안 된다.**

### 무엇이 무료이고 무엇이 돈이 드는가

| 구성요소 | 방식 | 비용 |
|---|---|---|
| 뉴스 수집 | Yahoo Finance RSS | 무료. 키·가입 불필요 |
| Stage 1 중복 제거 | 규칙 기반 | 무료 |
| Stage 2 클러스터링 | 로컬 ONNX 임베딩 | 무료 (첫 실행 시 ~120MB 1회 다운로드) |
| Stage 3 사건 매칭 | 로컬 벡터 비교 | 무료 |
| **Stage 4 사건 합성** | **mock (기본값)** | **무료** |
| 저장소 | SQLite 파일 1개 | 무료. 서버 아님 |
| Stage 4 사건 합성 | `anthropic` (선택) | **유료** — 월 $5~15 (§5.3) |

**돈이 나가는 경로는 Stage 4 하나뿐이고, `--provider anthropic`으로 명시적으로 켜야 한다.**

### SQLite는 "서버·DB 구축"이 아니다

"필요 없으면 DB를 만들지 않는다"는 원칙에 대해 한 가지는 유지하는 쪽이 맞다.
여기서 SQLite는 설치할 서버가 아니라 **파일 하나**이고, Node 22에 내장돼 있어 의존성조차 없다.

그리고 이 앱의 존재 이유(7일/30일 요약, 사건 기록장, 수집 공백 추적)는 전부 **영속성**에 의존한다.
메모리나 JSON 파일로 바꾸면 §3의 수집 공백 문제를 다시 만들게 된다. 비용은 0이고 대안이 더 나쁘다.

### mock의 설계 원칙

mock은 **산문을 쓰지 않는다.** 키워드 규칙으로 카테고리와 중요도를 정하고,
요약은 기사에 실제로 존재하는 필드(출처, 기사 수, 대표 스니펫)만 조립한다.

그럴듯한 가짜 분석을 생성하는 mock은 "파이프라인이 동작하는가"에 대해 **잘못된 확신**을 준다.
숫자·원인·평가를 지어내지 않는 것은 §1의 원칙을 mock에도 그대로 적용한 것이다.

또한 `other` 카테고리의 기본 가중치를 중요도 하한(40) 아래로 두었다. 그래야 조용한 날에
`NO_SIGNIFICANT` / `ONLY_FOLLOWUPS` 상태가 실제로 도달 가능하다 — 이 앱이 가장 정확해야 하는 상태다.

mock이 만든 사건은 `events.provider = 'mock'`으로 저장되고 UI에서 `[샘플]`로 표시된다.
샘플 텍스트가 실제 분석인 척하면 §1의 신뢰 원칙이 깨진다.

### 검증 순서

```
1. mock + 픽스처   네트워크·비용 0. 파이프라인 구조 확인
2. mock + 실제 RSS  비용 0. 2주간 매일 — Stage 1~3 임계값 튜닝이 여기서 끝난다
3. UI 붙이기        여전히 비용 0. 화면·빈 상태·사건 기록장 전부 mock으로 검증 가능
4. anthropic 전환   위가 다 되고 나서, "요약 문장 품질"만 남았을 때 켠다
```

**3단계까지 전부 무료로 갈 수 있다.** 유료가 필요한 시점은 구조가 아니라 문장 품질을 볼 때다.

### 금융 데이터도 같은 방식

시세·금리·환율·경제지표는 **아직 코드에 없다** (Phase 2). 붙일 때도 같은 순서를 따른다:
mock 어댑터 → 무료 소스(FRED, ECOS, RSS) → 필요하면 유료. §7의 소스 표는 그때 참조할 목록이지
지금 가입해야 할 목록이 아니다.

### Phase 0의 언어: TypeScript / Node 권장

CLI라도 언어는 정해야 하는데, 이건 지금 정하는 게 좋습니다 — Phase 0 코드가 그대로 남기 때문에.

| 후보 | 판단 |
|---|---|
| **TypeScript / Node** | **권장.** Phase 1에서 Electron이든 Tauri든 프론트가 TS라 백엔드를 그대로 재사용. 로컬 임베딩도 `onnxruntime-node` / `transformers.js`로 가능. `better-sqlite3` + `sqlite-vec` 조합이 안정적 |
| Python | 데이터·ONNX 생태계는 더 편하지만, Phase 1 데스크탑 앱과 연결이 끊긴다. Phase 0을 버리게 됨 |
| Rust | Tauri로 갈 게 확정이면 최선이지만, 스택을 보류한 상태에서 선택하기엔 이르다 |

→ **TypeScript로 진행.** 나중에 .NET이나 Rust로 UI를 가더라도, 수집기는 별도 실행 파일이라 그대로 두고 쓸 수 있다(스케줄러가 부르는 독립 프로세스이므로).

## 1. 제품 원칙 → 시스템 제약 번역

기획서의 철학은 좋은 말로 끝나면 안 되고 **코드가 강제하는 제약**이 되어야 한다.

| 기획서 원칙 | 시스템 제약 (검증 가능한 형태) |
|---|---|
| 14장. 사후 인과관계를 끼워 맞추지 않는다 | 사건 요약의 모든 문장은 **근거 기사 ID를 최소 1개** 가져야 한다. LLM 출력 스키마에서 `evidence: string[]` 를 required로 강제하고, 비어 있으면 그 문장을 버린다 |
| 22장. 모르는 것은 모른다고 한다 | LLM은 **숫자를 생성할 권한이 없다.** 주가·환율·금리·실적 수치는 전부 DB에서 온 값을 템플릿에 끼워 넣는다. 프롬프트에 숫자를 넣어주되 "입력에 없는 숫자는 쓰지 말 것"을 명시하고, 출력에서 입력에 없는 숫자 패턴을 후처리로 검출 |
| 8장. 왜 선택됐는지는 안 보여준다 | UI에는 노출 안 함. 단 **DB에는 반드시 기록**한다(`importance_reason`). 안 그러면 요약 품질이 나빠졌을 때 디버깅이 불가능하다 |
| 18장. 알림은 조용히 | 알림은 개별 사건이 아니라 **알림 큐**에 쌓고, 하루 최대 N회 배치 발송. 코드 레벨에서 rate limit |
| 12장. 금리는 대전제, 매일 해설 X | 금리 코멘트는 **변화 감지 트리거**로만 생성. 임계값(예: FOMC 확률 10%p 이상 변동, 10년물 15bp 이상 변동) 미달이면 LLM 호출 자체를 안 한다 |
| 5장. 특별한 일 없음도 알려준다 | "빈 상태"는 예외 처리가 아니라 **정식 렌더링 상태**. `NO_SIGNIFICANT_EVENTS` / `ONLY_FOLLOWUPS` / `NO_DATA(수집 실패)` 세 가지를 구분해야 한다 ← 셋을 뭉뚱그리면 앱이 거짓말을 한다 |

**마지막 줄이 특히 중요하다.** "별일 없었음"과 "수집이 실패해서 모름"은 완전히 다른데, UI에서 같아 보이면 이 앱의 신뢰도가 무너진다.

## 2. 전체 아키텍처

```
┌─────────────────────────────────────────────────────────┐
│  Collector (백그라운드 워커, 앱과 독립 실행)              │
│  - 뉴스 RSS/API 폴링                                      │
│  - 시세/금리/환율/경제지표 폴링                            │
│  - 캘린더(실적·경제지표 일정) 동기화                       │
└───────────────────────┬─────────────────────────────────┘
                        ↓  raw articles / series / calendar
┌─────────────────────────────────────────────────────────┐
│  Processor (파이프라인, LLM 비용이 여기서 결정됨)          │
│  Stage 1  규칙 기반 중복 제거     ← LLM 없음, 가장 많이 걸러냄 │
│  Stage 2  임베딩 클러스터링       ← 로컬 모델, 비용 0        │
│  Stage 3  LLM 사건 합성           ← 여기서만 돈이 든다       │
│  Stage 4  기존 사건 매칭 / 후속 판정                        │
└───────────────────────┬─────────────────────────────────┘
                        ↓
┌─────────────────────────────────────────────────────────┐
│  SQLite  (단일 파일 = 사용자 데이터 전부)                  │
│  events / articles / assets / series / calendar / digests │
└───────────────────────┬─────────────────────────────────┘
                        ↓  read-only 질의
┌─────────────────────────────────────────────────────────┐
│  UI (데스크탑 앱)                                          │
│  브리핑 / 자산 상세 / 시장 환경 / 예정 이벤트 / 인사이트      │
│  ※ UI는 LLM을 직접 호출하지 않는다 (조회 전용)              │
└─────────────────────────────────────────────────────────┘
```

**의도적으로 지킨 규칙 두 가지:**

1. **UI는 절대 LLM을 동기 호출하지 않는다.** 사용자가 앱을 켰을 때 "요약 생성 중... (30초)"를 보게 되면 이 앱의 목적(귀찮지 않음)이 깨진다. 모든 요약은 **이미 만들어져 있어야** 한다. UI는 DB 조회만 한다.
2. **Collector는 앱과 별개 프로세스여야 한다.** → 다음 절

## 3. ⚠️ 가장 큰 구조적 함정: 수집 공백

기획서 21장의 **"일주일 여행 다녀와서 앱을 켠다"** 시나리오가 이 설계에서 가장 어려운 부분이다.

문제: 데스크탑 앱은 꺼져 있으면 아무것도 못 한다. 그런데
- 무료 뉴스 API/RSS는 **과거 데이터를 거의 못 준다** (RSS는 보통 최근 20~50건, Finnhub company-news는 무료 티어에서 최근 1년 조회가 되지만 rate limit이 빡빡하고, Google News RSS는 과거 조회가 사실상 불가)
- 즉 **7일 동안 앱이 꺼져 있었으면, 그 7일의 뉴스는 영원히 사라진다.**
- 그러면 "지난 일주일 요약"과 "사건 기록장"이 성립하지 않는다. 이건 이 앱의 존재 이유 그 자체다.

**해법 (필수):** 수집기는 앱과 분리해서 **앱이 꺼져 있어도** 도는 구조여야 한다.

| 방식 | 설명 | 평가 |
|---|---|---|
| A. 트레이 상주 | 앱을 트레이에 상주시키고 주기 폴링 | 부분 해결. PC를 끄면 여전히 공백 |
| B. **Windows 작업 스케줄러 + 헤드리스 수집기** | 별도 실행 파일(또는 `--headless` 플래그)을 2~4시간마다 실행. 부팅 시 놓친 실행 자동 보충(`StartWhenAvailable`) | **1차 권장.** PC를 켜기만 하면 밀린 것을 따라잡는다 |
| C. 클라우드 수집기 | 초소형 VPS/서버리스가 24시간 수집, 앱은 동기화만 | 완전 해결이지만 개인용 1차에는 과함. **단, 나중에 배포할 거면 어차피 이 구조로 간다** |

**권장: B로 시작하되, Collector를 "언젠가 서버로 그대로 옮길 수 있는 독립 실행 바이너리"로 설계한다.** 그러면 C로의 이행이 재작성이 아니라 배포 위치 변경이 된다.

그리고 **수집 공백을 사용자에게 정직하게 표시해야 한다.** `job_runs` 테이블에 매 수집 시도를 기록하고, 공백이 있으면:

> 8/12 ~ 8/15 사이 뉴스를 수집하지 못했습니다. 이 기간의 사건은 누락되었을 수 있습니다.

이걸 숨기면 "별일 없었구나"라는 잘못된 안심을 주게 된다. 이 앱에서 그건 가장 나쁜 실패다.

## 4. 데이터 파이프라인 상세 (비용의 90%가 여기서 결정)

핵심 발상: **LLM에 도달하기 전에 최대한 줄인다.**

```
수집된 기사 300개/일
   │
   ├─ Stage 1  규칙 기반 제거 (LLM 0원)
   │    · URL 정규화(utm_* 제거, AMP/모바일 URL 통합) → 완전 중복 제거
   │    · 제목 정규화 후 토큰 Jaccard → 통신사 기사 재배포본 제거
   │      (당초 SimHash로 계획했으나 구현 중 변경 — 아래 참조)
   │      (같은 Reuters 기사가 야후/CNBC/네이버에 실린 것 = 1건으로)
   │    · 저품질 패턴 필터: "why X stock is moving today",
   │      "3 reasons to buy", 주가 등락만 다룬 제목 등 (기획서 4장 "잡음")
   │  → 약 300 → 80건
   │
   ├─ Stage 2  임베딩 클러스터링 (로컬 모델, 비용 0)
   │    · 제목+리드문 임베딩 (다국어 모델, 아래 5절)
   │    · 72시간 윈도우 내 코사인 유사도 임계값 기반 greedy 클러스터링
   │    · 클러스터당 대표 기사 1건 + 출처 다양성 상위 2~3건 선택
   │  → 80건 → 클러스터 12개
   │
   ├─ Stage 3  기존 사건 매칭 (로컬, 비용 0)
   │    · 각 클러스터 중심 벡터 vs 최근 30일 open 상태 사건 벡터 비교
   │    · 임계값 초과 → 기존 사건의 후속 (신규 사건 아님)
   │    · 미달 → 신규 사건 후보
   │  → 신규 후보 4개, 후속 8개
   │
   └─ Stage 4  LLM 사건 합성 ← 여기서만 과금
        입력: 신규 후보 4개 × (제목 + 2~3문장 스니펫 + 출처 + 시각)
             + 현재 열려 있는 사건 목록(제목만)
        출력: 구조화 JSON (사건 제목/요약/중요도/카테고리/근거 기사 ID)
      → 자산 1개당 하루 1회 호출, 입력 ~4K 토큰
```

**포인트:**
- 기사 **전문을 LLM에 넣지 않는다.** 제목 + 짧은 스니펫이면 사건 식별에 충분하다. 이것만으로 토큰이 10배 이상 줄고, 저작권 리스크도 같이 줄어든다.
- 후속 보도(8개)는 **LLM을 안 거친다.** 기존 사건에 기사만 붙이고 `last_updated_at`만 갱신. 기획서 4장의 "반복/후속"이 자동으로 조용해진다.
- 기간별 요약(7일/30일)은 **원본 뉴스를 다시 안 본다.** 이미 만들어진 사건 목록을 중요도순으로 정렬해서 상위 N개를 뽑고, 한줄 요약만 짧은 LLM 호출로 생성한다.

### Stage 1은 SimHash가 아니라 토큰 Jaccard (구현 중 변경)

SimHash는 문서 수백만 건을 다룰 때 맞는 도구다. 그런데 **제목은 너무 짧아서** 비트 시그니처가 소수의
토큰에 좌우되고, 실제 중복을 놓치면서 무관한 기사를 합치기도 한다. Phase 0 규모(실행당 수백 건)에서는
O(n²) 정확 비교가 수 밀리초라 훨씬 정확한 쪽을 택했다. 실행당 5천 건을 넘기면 재검토한다.

### clusterThreshold는 0.78이 아니라 0.95였다 (실측)

첫 로컬 실행에서 픽스처의 서로 다른 4개 사건이 **전부 하나로** 뭉쳤다. 원인 두 가지가 겹쳤다.

1. **e5 계열 임베딩의 기저 유사도가 높다.** 한 기업에 대한 짧은 헤드라인은 주제가 완전히 달라도
   ("자동차 부문 인사" vs "중국 H200 규제 조사") 코사인이 0.8을 훌쩍 넘는다. 문서 유사도용으로
   설계된 임계값 직관이 헤드라인에는 통하지 않는다.
2. **Greedy 병합의 centroid drift.** 기사를 추가할 때마다 centroid를 재계산하므로, centroid가
   조금씩 다음 주제 쪽으로 끌려가며 원래 무관했던 기사까지 임계값 안으로 들어온다. 연쇄적으로
   전부 한 덩어리가 된다.

→ **0.95.** 이 값에서 픽스처가 의도한 4개 사건으로 갈라진다. 구성까지 확인했다 (2026-08-19):

```
[1] Reuters + Financial Times — Oracle 계약  ← 어휘가 다른 두 기사가 합쳐짐 (Stage 2의 존재 이유)
[2] H200 공급
[3] 중국 규제 조사
[4] 자동차 인사
```

**주의: 이 값은 임베딩 모델에 종속된다.** `embeddingModel`을 바꾸면 반드시 다시 측정해야 한다.
모델마다 유사도 분포가 다르므로 0.95라는 숫자 자체에는 의미가 없다.

### 왜 이 버그를 테스트가 못 잡았나 (일반화할 것)

기존 테스트는 스텁 임베더를 쓴다. 스텁은 주제별로 깔끔하게 분리된 인위적 벡터를 만들어내므로,
**클러스터링 로직은 검증하지만 임계값이 실제로 맞는지는 검증하지 못한다.** 실제 모델의 유사도
분포가 예상과 다르다는 것이 이 버그의 본질이고, 그건 정의상 스텁으로 재현할 수 없다.

여기서 나온 도구가 `collect --verbose`다. **클러스터 개수만으로는 과병합과 과분할을 구분할 수
없다** — 기사 5건이 클러스터 4개가 되는 것은 *올바른 쌍*이 합쳐졌을 때만 맞다. 임계값을 만질
때는 항상 구성(무엇이 무엇과 묶였는지)을 봐야 한다.

### 0.95의 반대편 위험

임계값이 높으면 과병합 대신 **과분할**이 온다. 같은 사건을 다룬 두 기사가 어휘가 많이 다르면
0.95를 못 넘고 사건이 둘로 쪼개진다 → 사용자에게 중복 사건이 보인다.

픽스처의 Reuters/FT Oracle 기사 쌍이 이 경계선의 기준점이다. 실제 RSS로 며칠 돌리면서
**양쪽 실패를 다 봐야 한다.** 한쪽만 보고 조이면 반대쪽이 깨진다.

### 첫 실전 수집에서 나온 것 (2026-08-19)

스케줄러로 실제 Yahoo RSS를 처음 받자마자 두 가지가 드러났다.

**1. Yahoo의 종목별 피드는 종목 뉴스가 아니다.** 일반 시황 기사가 섞여 들어온다.
`Stock Market Today: Dow Rises On Treasury Buybacks`, `15 S&P 500 stocks are up 100% or more`
같은 것들이 잡음 필터를 빠져나가 **사건으로 승격됐다.** 패턴 3개를 추가했다
(`stock-market-today`, `index-roundup`, `numbered-stock-list`).

여기서 얻은 교훈은 패턴 3개가 아니라 **소스 품질이 Stage 1의 부하를 결정한다**는 것이다.
피드를 늘릴 때마다 잡음 패턴을 다시 봐야 한다.

**2. 잡음 하나가 무관한 사건의 후속으로 붙었다.** "15 S&P 500 stocks…"가 Oracle 데이터센터
사건의 후속 보도로 기록됐다. 잡음을 걸러내면 이 사례는 사라지지만, **원인은 그대로 남아 있다.**

`clusterThreshold`를 0.78 → 0.95로 올려야 했던 것과 같은 이유가 `eventMatchThreshold`(현재 0.75)에도
적용된다. 같은 기업에 대한 짧은 텍스트는 무관해도 코사인이 높게 나온다. **0.75는 거의 무엇이든
열린 사건에 붙인다.**

다만 이건 클러스터링과 분포가 다르다 — 여기서는 기사 묶음의 centroid를 **사건 제목+요약** 임베딩과
비교하므로, 텍스트의 성격이 다르다. 그래서 0.95를 그대로 옮겨 쓰면 안 되고 따로 측정해야 한다.

→ 측정 도구로 `collect --verbose`에 **Stage 3의 최근접 점수**를 추가했다. 임계값을 넘겼든
아니든 모든 클러스터에 대해 "가장 가까운 열린 사건과 그 점수"를 출력한다. 채택된 매칭만 보면
아깝게 놓친 것도, 아깝게 붙은 것도 보이지 않는다.

### 자산 4개로 늘리자마자 드러난 것: 피드가 종목 뉴스가 아니다

관심자산을 NVDA 하나에서 4개로 늘린 순간 진짜 문제가 보였다.

| 자산 | 피드 12~14건 중 실제로 그 자산에 대한 기사 |
|---|---|
| DELL | 3~5건. 나머지는 Sandisk, Micron, Vanguard ETF, Penguin Solutions, Cisco |
| WDC | 1~2건. 나머지는 Micron, Cerebras, Intel, AMD, SpaceX, KOSPI |
| NVDA | 소수. 나머지는 Unitree IPO, SpaceX, Anthropic, Berkshire, Palantir, Nebius |

**이건 잡음이 아니다.** 전부 진짜 사건을 다룬 멀쩡한 기사다 — 다만 **다른 회사** 이야기다.
헤드라인 모양으로 거르는 잡음 패턴으로는 원리적으로 잡을 수 없다. 주제의 문제다.

그 결과 브리핑에 "DELL — 중요 사건 6건"이 떴는데 그중 Dell 이야기는 절반뿐이었다.
이 앱의 목적("읽지 않아도 중요한 일은 안다")이 정면으로 깨지는 실패다.

**원인: `aliases`가 설정에만 있고 파이프라인에서 안 쓰이고 있었다.** 설계서 §8의
`article_assets(article_id, asset_id, match_method)`가 관련성 판정을 전제하고 있었는데,
Phase 0 구현에서 그 단계가 통째로 빠져 있었다.

→ Stage 1에 관련성 필터를 추가했다 (`pipeline/relevance.ts`, `off_topic`).
제목이나 리드에 **심볼·한글명·별칭 중 하나가 명시돼야** 통과한다.

의도적으로 무딘 규칙이다. 회사 이름이 한 번도 안 나오는 기사를 놓치는 비용은,
브리핑의 절반이 남의 회사 이야기인 것보다 훨씬 싸다.

**잡음 필터와 분리해서 둔 이유:** 둘은 다르게 실패한다. 잡음 패턴이 잘못되면 특정 *모양*의
헤드라인이 사라지고, 별칭 목록이 잘못되면 **그 자산의 피드가 통째로** 사라진다.
같은 함수에 섞으면 어느 쪽이 원인인지 알 수 없게 된다.

**티커는 대소문자를 구분해서 매칭한다.** 짧은 티커는 영어 단어와 겹친다 — `ON`, `IT`, `ALL`,
`SO`가 전부 실제 상장 종목이고 `A`는 Agilent다. 소문자까지 허용하면 ON Semiconductor의 피드가
"on"이 들어간 모든 기사를 받아들인다.

### 과필터링은 테스트로만 막을 수 있다

`index-roundup` 패턴의 초안은 `(dow|nasdaq).*(rises|closes|…)` 였는데, 이게
**"Nasdaq-listed Nvidia closes $8 billion Oracle deal"** — 진짜 사건 — 을 잡음으로 버렸다.
`.*`가 제목 전체를 건너뛰어 무관한 두 단어를 이어붙인 것이다.

가드 테스트(`test/noise.test.ts`의 `SIGNAL` 목록)가 즉시 잡아냈다. **잡음 패턴을 추가할 때는
반드시 그 패턴이 잘못 잡을 만한 진짜 헤드라인을 함께 추가한다.** 잡음을 놓치는 것보다 진짜
사건을 버리는 것이 훨씬 나쁜 실패이고, 후자는 조용히 일어나기 때문이다.

### Stage 1이 과하게 합치면 안 된다

같은 사건을 다뤘지만 **어휘가 다른** 기사(예: Reuters "$8 billion data center expansion" vs
FT "build new AI data center capacity in $8bn deal")는 Stage 1이 합치면 안 된다. 규칙으로는 알 수 없고,
그걸 알아내라고 Stage 2 임베딩이 있는 것이다. 임계값을 조이다가 이 둘이 합쳐지기 시작하면
**Stage 2가 할 일을 뺏긴 것이고, 곧 진짜 사건이 사라지기 시작한다.**

### 중요도 점수의 안정성 (놓치기 쉬운 문제)

같은 사건이 실행할 때마다 중요도 점수가 흔들리면 사건 기록장이 매일 재배열된다. → **중요도는 사건 생성 시점에 1회 확정하고 불변으로 둔다.** 후속 보도가 붙으면 `followup_count`만 증가시키고, 정말 큰 변화(예: 규제 "검토" → 규제 "확정")일 때만 **새 사건으로 승격**한다. 이 승격 판단은 LLM에게 명시적으로 물어야 한다.

### 사건의 종료

사건이 언제 닫히는지 정의가 없으면 30일 뒤에도 계속 후속 매칭이 된다. → **마지막 관련 기사 이후 7일 경과 시 `closed`.** closed 사건은 매칭 대상에서 빠지고, 같은 주제가 다시 나오면 새 사건이 된다.

이 규칙 하나가 **매칭 대상 집합도 함께 결정한다.** open 사건은 정의상 7일보다 오래 방치될 수 없으므로,
"몇 일까지 거슬러 매칭할지"를 별도 설정으로 두면 중복이고, 실제로 구현 중 버그가 됐다 —
종료 판정을 최근 30일 슬라이스에만 걸었더니 **그보다 오래된 사건은 판정 대상에 못 들어와 영원히 열려 있었다.**
종료 판정은 반드시 `status='open'`인 **전체**를 훑어야 한다.

### 버린 중복은 다음 실행에 되살아난다 (Phase 0에서 발견)

RSS는 매 실행마다 같은 창을 다시 준다. 그런데 near-duplicate로 버린 기사는 DB에 저장되지 않으므로,
다음 실행에서 "이미 아는 URL" 목록에 없어서 통과한다. → **실행할 때마다 같은 사건의 사본이 하나씩 늘어난다.**

따라서 중복 판정은 저장된 URL만이 아니라 **저장된 기사의 정규화 제목까지** 기억해야 한다.
URL은 전체 이력에서 확인하고(1년 전 링크의 재게시도 재게시다), 제목은 수집 기간 내에서만 비교한다
(몇 달 떨어진 무관한 두 사건이 비슷한 제목 형태를 가질 수 있다).

## 5. AI 사용 설계

### 5.1 임베딩은 로컬, 생성은 API

Anthropic은 임베딩 API를 제공하지 않는다. 클러스터링용 임베딩은 **로컬 모델**로 돌리는 것을 권장한다:

- 후보: `bge-m3`, `multilingual-e5-small/base` 등 다국어 모델 (한국어 기사와 영어 기사를 같은 공간에 놓아야 하므로 다국어가 필수)
- 실행: ONNX Runtime (CPU로 충분. 하루 수백 건 수준)
- 이유: **비용 0원, 네트워크 0, rate limit 0.** 클러스터링은 하루 수백~수천 번 도는 연산이라 API로 하면 그 자체가 비용이 된다.
- 대안(로컬 모델 세팅이 부담스러우면): Voyage AI 임베딩 API. 다만 무료 티어 한도와 지연을 감수해야 함.

### 5.2 생성 모델 선택

| 용도 | 권장 모델 | 근거 |
|---|---|---|
| **사건 합성 / 중요도 판단** | `claude-opus-5` | 이 앱의 품질 전부가 이 판단에 달려 있다. 자산당 하루 1회, 입력 4K 토큰이라 절대 비용이 작다. 여기서 아끼면 앱이 무의미해진다 |
| 기간별 한줄 요약 | `claude-opus-5` (동일 호출에 묶어도 됨) | 별도 호출 자체가 불필요할 수 있음 |
| 저품질 기사 사전 분류(선택) | `claude-haiku-4-5` | Stage 1 규칙으로 안 잡히는 것만. 굳이 안 해도 됨 |
| 오늘의 인사이트 3 큐레이션 | `claude-opus-5` | 하루 1회 |

현재 가격(2026-06 기준, 1M 토큰당):

| 모델 | 입력 | 출력 | 컨텍스트 |
|---|---|---|---|
| `claude-opus-5` | $5.00 | $25.00 | 1M |
| `claude-sonnet-5` | $3.00 (2026-08-31까지 $2.00 프로모) | $15.00 ($10.00) | 1M |
| `claude-haiku-4-5` | $1.00 | $5.00 | 200K |

### 5.3 비용 추정 (관심자산 10개 기준)

| 항목 | 일일 토큰 | 일일 비용 |
|---|---|---|
| 사건 합성 (10자산 × 1회 × 입력 4K / 출력 800) | 입력 40K / 출력 8K | $0.20 + $0.20 = **$0.40** |
| 시장 환경(금리·환율) 변화 시에만 | 주 2~3회, 회당 3K | ~$0.01/일 |
| 오늘의 인사이트 3 (후보 30건 → 3건 선별) | 입력 20K / 출력 1K | **$0.13** |
| **합계** | | **약 $0.55/일 ≈ $17/월** |

**절감 수단 (적용 시 절반 이하):**

1. **Batch API — 50% 할인.** 야간 수집은 실시간성이 전혀 필요 없다. 이 파이프라인은 배치에 완벽하게 맞는다. → **$17 → $8.5/월**
2. **프롬프트 캐싱.** 시스템 프롬프트(사건 판단 기준 + 출력 스키마 + 원칙)는 자산마다 동일하고 몇 주간 안 바뀐다. 10개 자산을 연속 호출하면 시스템 프롬프트가 캐시 히트한다. 단 **캐시는 접두사 완전 일치**이므로, 시스템 프롬프트에 날짜/자산명 같은 가변값을 절대 넣으면 안 된다(가변값은 전부 `messages` 뒤쪽으로).
3. **신규 클러스터 0개인 자산은 LLM 호출 자체를 건너뛴다.** DELL 같은 조용한 종목은 대부분의 날에 호출이 없다. 실제로는 위 추정보다 훨씬 적게 나올 가능성이 높다.
4. **일일 토큰 상한(circuit breaker).** 예상치 못한 뉴스 폭증 시 비용이 튀지 않도록 하드 리밋을 두고, 초과 시 중요도 상위 자산만 처리.

> 정리: **개인 사용 기준 월 $5~15 수준.** 이 정도면 모델을 아끼기보다 품질을 택하는 게 맞다.

### 5.4 출력은 반드시 구조화 (Structured Outputs)

사건 합성 결과는 자유 텍스트가 아니라 스키마로 받는다. `output_config.format`(구조화 출력) 또는 `strict: true` 툴 스키마를 사용:

```jsonc
{
  "events": [{
    "title": "중국향 H200 공급 관련 새로운 움직임",   // 12~30자, 사건명이지 기사 제목이 아님
    "summary": "…",                                  // 2~4문장
    "importance": 78,                                // 0-100
    "category": "regulation|earnings|product|deal|management|macro|other",
    "evidence": ["art_1042", "art_1055"],            // required, 비면 폐기
    "relates_to_open_event": "evt_331" | null,       // 후속이면 사건 ID
    "promote_to_new_event": false,                   // 후속이지만 새 사건으로 승격할지
    "certainty": "reported|confirmed|speculative"     // speculative는 UI에서 톤을 낮춤
  }],
  "period_summary": "…",       // 한줄 요약
  "no_significant_events": false
}
```

`certainty` 필드는 기획서 14장·22장을 지키기 위한 장치다. "~로 보인다" 수준의 이야기와 "발표됐다"를 UI에서 다르게 표현할 수 있어야 한다.

### 5.5 프롬프트에 반드시 들어가야 할 금지 규칙

기획서의 원칙을 프롬프트 규칙으로 옮긴 것:

- 입력에 없는 숫자·날짜·인용을 만들어내지 말 것
- 주가 움직임의 **원인을 단정하지 말 것**. 원인이 명시된 기사가 있을 때만 그 기사를 근거로 인용
- 여러 요인이 가능하면 나열하되 어느 것이 원인이라고 결정하지 말 것
- 기사 제목을 그대로 쓰지 말 것 (사건 이름을 지을 것)
- 사소한 것을 억지로 채워 넣지 말 것 — **사건이 0개면 0개로 반환할 것**

마지막 줄이 실제로 가장 안 지켜지는 항목이다. LLM은 빈 배열을 반환하기 싫어한다. → 프롬프트에 명시하고, **평가 시 "조용한 날"을 일부러 테스트 케이스에 넣어야 한다.**

### 6.1 데스크탑 앱

| 옵션 | 장점 | 단점 | 평가 |
|---|---|---|---|
| **Tauri 2 + React/TS** | 설치 파일 ~10MB, 메모리 적음, 시스템 트레이/알림/자동시작 플러그인 완비, Rust 백엔드로 수집기까지 한 바이너리 | Rust를 일부 만져야 함 | **권장** (트레이 상주형 앱에 가장 잘 맞음) |
| Electron + React/TS | 생태계 최대, 전부 TS로 해결, `safeStorage`로 키 보관 간단 | 설치 ~150MB, 메모리 큼 | 무난한 차선 |
| .NET 8 + WinUI 3 / WPF | Windows 네이티브, 작업 스케줄러·토스트 알림 연동이 가장 자연스러움 | UI 개발 속도가 웹보다 느림, LLM/뉴스 생태계 라이브러리가 적음 | Windows 전용 확정이고 C#이 익숙하면 |
| Python + PySide6 | 데이터/AI 라이브러리 최강 | 배포/패키징이 번거로움 | 프로토타입용으로만 |

**권장: Tauri 2 + React + TypeScript.** 다만 이건 **Rust 경험 여부에 전적으로 달려 있다.** Rust가 부담스러우면 Electron이 정답이다 — 이 앱에서 성능은 병목이 아니다.

> 참고: 어떤 스택을 고르든 **Collector 로직은 UI 프레임워크에 의존하지 않게 분리**한다. 나중에 서버로 옮기거나 스케줄러에서 직접 실행해야 하기 때문.

### 6.2 저장소

**SQLite 단일 파일.** 논쟁의 여지 없음.
- 벡터 검색: `sqlite-vec` 확장 (사건 수천 개 규모라 브루트포스 코사인도 충분하지만, 확장을 쓰면 코드가 깔끔)
- 전문 검색: `FTS5` (사건 기록장에서 검색할 때)
- 백업: 파일 하나 복사. 사용자 데이터가 전부 한 파일에 있다는 게 개인용 앱에서 큰 장점

### 7.2 FOMC 확률에 대한 보충 (기획서 12장 대응)

기획서에 "금리 전망의 숫자는 AI가 추측하지 않고 실제 시장 데이터를 사용한다"고 명시돼 있는데, 이게 생각보다 까다롭다.

- FedWatch 수치를 그대로 쓰는 무료·합법 API가 사실상 없다.
- **해법:** 연방기금 선물 가격으로 직접 계산한다. `내재 금리 = 100 − 선물가격`. 이걸 현재 정책금리 목표 범위와 비교하면 동결/인하 반영 확률이 나온다. 계산식은 공개돼 있고 결정론적이라 **AI가 개입할 여지가 없다** — 기획 의도에 정확히 부합한다.
- 그리고 AI는 "확률이 크게 변했을 때 그 시점의 경제 이벤트를 요약"하는 역할만 맡는다.

### 7.3 API 한도 관리

무료 티어 10개 자산 × 여러 소스면 금방 한도를 넘긴다. Collector에 **소스별 토큰 버킷 + 지수 백오프 + 429 응답 존중**을 넣어야 한다. 이건 나중에 붙이면 이미 밴 당한 뒤라서, 처음부터 넣는 게 맞다.

### 7.4 저작권 (중요)

- **기사 전문을 저장·표시하지 않는다.** DB에는 제목 + 리드 2~3문장 + 출처 + 원문 URL + 발행시각만.
- 화면에 보이는 것은 **AI가 생성한 사건 요약**과 **원문 링크**뿐 — 기획서 7장이 이미 이 방향이라 다행히 설계가 맞아떨어진다.
- 개인 사용과 배포는 법적 지위가 다르다. 13절 참조.

## 8. 데이터 모델 (스키마 초안)

```sql
-- 관심자산
assets(id, symbol, name, asset_class, exchange, enabled, sort_order, added_at)

-- 원본 기사 (전문 저장 안 함)
articles(id, url_canonical UNIQUE, title, source, author,
         published_at, snippet, lang, simhash, fetched_at)
article_assets(article_id, asset_id, match_method)   -- 어떤 자산과 연결됐는지
article_vec(article_id, embedding BLOB)

-- 사건 ★ 이 앱의 중심
events(id, asset_id, title, summary, importance, category,
       certainty,                       -- reported | confirmed | speculative
       status,                          -- open | closed
       parent_event_id,                 -- 승격된 경우 원 사건
       first_seen_at, last_updated_at, followup_count,
       importance_reason,               -- UI 비노출, 디버깅 전용
       source_run_id)                   -- 어느 실행이 만들었나
event_articles(event_id, article_id, is_primary)
event_vec(event_id, embedding BLOB)     -- 후속 매칭용

-- 시계열 (금리, 환율, 지수, 시세)
series(id, source, code, name, unit)
series_points(series_id, ts, value)     -- PK(series_id, ts)

-- 캘린더: 예정 → 발생 → 사건으로 승격
calendar_events(id, asset_id NULL, kind, title, scheduled_at, tz,
                consensus_json,          -- 예상 매출/EPS 등
                actual_json,             -- 발표 후 실제치
                status,                  -- scheduled | occurred | promoted
                promoted_event_id)

-- 기간 요약 캐시
digests(id, scope, scope_id, window, generated_at,
        oneliner, payload_json, state)   -- state: HAS_EVENTS | NO_SIGNIFICANT | ONLY_FOLLOWUPS | NO_DATA

-- 오늘의 인사이트 3
insights(id, date, title, source, url, topic, why_selected, shown)

-- 운영
job_runs(id, job, started_at, finished_at, ok, error, stats_json)  -- ★ 수집 공백 추적
user_feedback(id, event_id, verdict, created_at)                    -- 👍 / "이건 사소함"
settings(key, value)
```

`user_feedback`이 왜 필요한가: 기획서 8장에 따라 "왜 선택했는지"를 사용자에게 안 보여주기로 했다. 그러면 **요약 품질이 나빠져도 알 방법이 없다.** 최소한의 피드백 버튼(이 사건은 사소했다) 하나만 있으면 나중에 중요도 임계값과 프롬프트를 튜닝할 근거가 생긴다. UI에서는 아주 작게, 눈에 안 띄게.

## 9. 예정 이벤트 파이프라인 (기획서 15~17장)

```
calendar_events(status=scheduled)
   │  scheduled_at 도래
   ↓
status=occurred  + 결과 데이터 수집(실제 EPS/매출, 지표 실측치)
   │  실측치 vs 컨센서스 비교
   ↓
events 테이블로 승격 (status=promoted, promoted_event_id 연결)
   │
   ↓
"최근 사건"에 등장 → 시간이 지나면 사건 기록장으로
```

- **알림은 D-0 1회만.** 기획서 16장대로 24h/12h/1h 반복 알림 없음.
- 발표 후 결과 표시에서 **숫자는 전부 DB 값**, AI는 한줄 코멘트만.
- 경제지표(CPI 등)는 `asset_id = NULL`인 시장 전역 이벤트로 둔다.

## 10. 알림 설계

```
사건 생성 → 알림 후보 큐 적재
   ↓ 게이트
   · importance ≥ 임계값(기본 75)
   · 해당 사건이 신규(후속 아님)
   · 조용한 시간대(기본 23:00~08:00 KST) 아님
   · 오늘 이미 N회(기본 2회) 보냈으면 다음 배치로 미룸
   ↓
배치 묶음 발송: "NVDA · BTC — 중요한 사건 3건"
```

- Windows 토스트 알림 사용 (Tauri: notification 플러그인 / Electron: `Notification` / .NET: `ToastNotification`)
- **알림 클릭 → 해당 사건 상세로 직행**
- "특별한 일 없음"은 **알림을 보내지 않는다.** 조용한 게 정상 상태다.
- 사용자가 임계값을 바꿀 수 있게 하되, 슬라이더가 아니라 **"조용히 / 보통 / 민감"** 3단계로 노출 (숫자를 노출하면 튜닝 압박을 준다)

## 12. UI/UX 제안

기획서에서 "UI는 아직 정하지 않았으니 제안해달라"고 하셔서, **기능이 아니라 사용 상황에서 역산**했다.

### 12.1 이 앱의 진짜 사용 패턴

사용자는 이 앱을 **오래 보지 않는다.** 목표는 "30초 안에 닫는 것"이다. 그렇다면 UI의 성공 기준은:

> **앱을 켠 지 5초 안에, 스크롤 없이, "별일 없음 / 뭔가 있음"을 알 수 있는가?**

일반적인 대시보드(차트, 숫자 타일, 히트맵)는 이 목표에 **정면으로 반한다.** 정보 밀도가 높으면 스캔에 시간이 걸리고, 그 자체가 피로다. 그래서 이 앱의 UI는 **의도적으로 비어 있어야 한다.**

### 12.3 설계 결정과 근거

**① 기간 선택의 기본값은 "마지막 방문 이후"**
`24시간/7일/30일` 고정 탭이 아니라, 앱을 열면 `last_opened_at` 기준으로 **"지난 8일 동안"** 이 자동 선택된다. 기획서 21장의 여행 시나리오가 특수 케이스가 아니라 **기본 동작**이 된다. 24h/7d/30d는 그 옆의 보조 토글.

**② 사이드바의 점(●)이 이 UI의 핵심 발명**
자산별 중요 사건 개수를 점 1~3개로 표시. **숫자도 색도 아닌 점.** 이유:
- 빨강/초록은 주가 등락을 연상시키는데, 이 앱은 등락을 다루지 않는다 → 오해를 만든다
- `─` (사건 없음)이 시각적으로 **가장 조용해야** 한다. 기획서 5장의 "별일 없구나"를 0.5초 만에 전달
- 전부 `─`면 앱을 그냥 닫으면 된다. 이게 이 앱의 **성공한 사용 경험**이다

**③ 사건 카드는 기본 접힘, 관련 기사는 2단 접힘**
```
① 사건 제목                      ← 항상 보임
   요약 2~4문장                   ← 항상 보임
   ▸ 관련 기사 3                  ← 클릭해야 펼쳐짐
      Reuters · 제목 한 줄
      Bloomberg · 제목 한 줄
```
기획서 7장의 "원문이 주인공이 되면 안 된다"를 레이아웃으로 강제한다. 원문 링크에 도달하려면 클릭이 2번 필요하고, 그건 의도된 마찰이다.

**④ 차트를 넣지 않는다 (1차 기준)**
"시장 환경"은 숫자 타일이 아니라 **문장**으로 표시한다. `USD/KRW 1,385.20 ▲0.3%` 대신 `환율 — 높은 수준 유지, 최근 3주 상단 횡보`. 기획서 11장의 "숫자를 잔뜩 보여주는 것이 목적이 아니다"와 13장(현재 수준/추세/과거 대비)을 그대로 반영. 정확한 숫자는 클릭하면 나온다.

**⑤ 빈 상태를 1급 디자인 대상으로**
| 상태 | 표시 |
|---|---|
| `NO_SIGNIFICANT` | "특별히 새로운 중요한 사건은 없습니다" (회색, 담담하게) |
| `ONLY_FOLLOWUPS` | "최근 뉴스는 대부분 기존 이슈의 후속 보도입니다" |
| `NO_DATA` | 아래 3가지로 다시 갈린다 |

**앞의 둘은 실패가 아니라 성공 상태**로 보여야 한다. 스켈레톤이나 "데이터 없음" 같은 개발자 언어를 절대 쓰면 안 된다.

**`NO_DATA`의 3가지 하위 상태** (Phase 0 구현 중 발견 — 처음 설계에는 없었다):

| 하위 상태 | 조건 | 표시 |
|---|---|---|
| `never` | 이 자산을 한 번도 수집한 적 없음 | ℹ "아직 수집한 적이 없습니다" |
| `cold_start` | 수집은 시작했으나 조회 기간이 그 이전까지 걸침 | ℹ "8/19부터 수집을 시작했습니다. 그 이전 기간은 확인되지 않았습니다" |
| `outage` | 수집하다가 중간에 끊김 | ⚠ "8/12~8/15 사이 수집하지 못했습니다" |

**셋을 뭉뚱그리면 앱이 거짓말을 한다.** 자산을 방금 추가한 사용자에게 "수집에 실패했습니다"라고 말하는 건
사실이 아니고, 이 앱이 절대 틀리면 안 되는 신호가 바로 그것이다. 경고 톤(⚠)은 `outage`에만 쓴다.

**⑥ 사건 기록장은 자산 상세의 타임라인 탭**
평소엔 숨어 있고(기획서 6장), 자산을 클릭하면 나오는 화면에 `최근 사건 / 기록장 / 예정` 3탭. 기록장은 날짜 그룹 리스트.

**⑦ 톤**
- 다크 모드 기본, 채도 낮게. 빨강/초록은 실적 실측치 vs 컨센서스 비교에서만 제한적으로 사용
- 애니메이션 최소, 배지·카운터·"NEW" 표시 없음 (전부 사용자를 재촉하는 장치다)
- 새로고침 버튼은 있되 눈에 안 띄게. 마지막 수집 시각을 작게 상시 표시

**⑧ 오늘의 인사이트 3 (기획서 23장)**
홈 최하단, 또는 사이드바 별도 항목. **브리핑과 섞지 않는다.** 브리핑은 "확인"이고 인사이트는 "공부"라 사용 맥락이 다르다. 좋은 콘텐츠가 3개 없으면 **1개만 보여주거나 아예 안 보여준다** (기획서 19장 원칙).

## 13. 개인용 vs 배포용의 차이

| 항목 | 개인용 (1차) | 배포 시 |
|---|---|---|
| **API 키** | 사용자 PC에 DPAPI로 저장, 클라이언트가 직접 호출 | **불가능.** 바이너리에 키를 넣으면 즉시 추출된다 → 서버 프록시 필수, 또는 BYO-key(사용자가 자기 키 입력) |
| **LLM 비용** | 월 $5~15, 내가 부담 | 사용자 수에 비례해 폭증 → **아래 ★ 참조** |
| **뉴스 데이터** | 무료 티어, 사적 이용 | 상업 라이선스 필요. Finnhub·NewsAPI 등 무료 티어는 상업적 재배포 금지 |
| **저작권** | 개인 열람 목적 | 제목·스니펫 표시도 언론사별 약관 확인 필요 |
| **규제** | 없음 | 금융 정보 제공 관련 고지 필요("투자자문이 아님"), 국내 유사투자자문업 해당 여부 검토 |
| **업데이트** | 수동 | 자동 업데이터, 크래시 리포팅, 원격 프롬프트 갱신 |

### ★ 배포 시 비용 구조가 바뀌는 지점 (지금 대비해두면 좋은 것)

개인용에서는 "사용자 1명 × 자산 10개 = 하루 10회 호출"이다.
배포하면 "사용자 1,000명 × 자산 10개 = 하루 10,000회"가 될 것 같지만 — **아니다.**

> NVDA에 대한 사건 요약은 **모든 사용자에게 동일하다.**

즉 서버에서 **자산 단위로 1회만 생성해서 전 사용자가 공유**하면, 비용은 사용자 수가 아니라 **관심자산 종류 수**에 비례한다. 1,000명이 써도 하루 수백 회면 충분하다. 이게 이 제품이 사업적으로 성립할 수 있는 이유다.

**그래서 지금 해둘 것:** 파이프라인을 처음부터 두 층으로 나눠 설계한다.

- **공용 층** (자산별 사건 생성, 시장 환경, 캘린더) → 나중에 그대로 서버로 올라간다
- **개인 층** (관심자산 목록, 필터, 알림 임계값, 읽음 상태, 피드백) → 클라이언트에 남는다

이 경계만 지켜두면 배포 전환이 **재작성이 아니라 배포 위치 변경**이 된다. 지금 추가 비용은 거의 0이고, 나중에 아끼는 시간은 몇 주다.

## 14. 기획에서 빠졌거나 위험한 것

우선순위 순.

| # | 항목 | 왜 문제인가 | 대응 |
|---|---|---|---|
| 1 | **수집 공백** | 앱이 꺼져 있으면 그 기간 뉴스는 영원히 소실 → 7일/30일 요약이 성립 안 됨 | 3절 (헤드리스 수집기 + 스케줄러) |
| 2 | **콜드 스타트** | 앱을 처음 설치하거나 자산을 새로 추가하면 사건 기록장이 텅 빔. 그런데 무료 소스는 과거 조회가 어려움 | 신규 자산 추가 시 백필 루틴(가능한 만큼) + "수집 시작 시점" 명시 표시. 완벽히 못 채운다는 걸 인정하고 정직하게 표시 |
| 3 | **"별일 없음"과 "모름"의 혼동** | 이 앱 신뢰도의 근간 | 1절, 12.3-⑤ (3가지 상태 분리) |
| 4 | **중요도 점수 불안정** | 매 실행마다 순위가 바뀌면 기록장이 흔들림 | 4절 (생성 시 확정, 불변) |
| 5 | **시간대 정의 부재** | 미국장/한국장/UTC 혼재. "어젯밤 무슨 일이 있었나"의 정의가 없음 | 저장은 전부 UTC, 표시는 KST. **"어젯밤" = 전일 22:00 ~ 당일 08:00 KST** 로 명시적 정의(미국 정규장이 여기 들어옴) |
| 6 | **언어 혼합** | 소스는 영문, 출력은 한국어. 고유명사 표기 흔들림("엔비디아"/"NVIDIA"/"Nvidia") | 프롬프트에 표기 규칙 고정 + 자산별 한글명을 `assets` 테이블에 저장해 주입 |
| 7 | **품질 측정 수단 없음** | 8장에 따라 근거를 안 보여주기로 했으므로, 요약이 나빠져도 감지 불가 | `importance_reason` DB 기록 + 최소 피드백 버튼 (8절) |
| 8 | **실적 컨센서스 신뢰도** | 무료 소스마다 값이 다르고, 발표 직전 갱신됨 | 출처와 기준 시각을 함께 표시. 단일 소스 고정 |
| 9 | **API rate limit** | 자산 10개 × 소스 5개면 무료 티어 즉시 초과 | 7.3절 (토큰 버킷, 처음부터) |
| 10 | **LLM 비용 폭주** | 대형 뉴스 이벤트 발생 시 기사 수가 10배 | 일일 토큰 상한 + 초과 시 상위 자산만 처리 |
| 11 | **오프라인/장애 UX** | API 장애 시 화면이 깨지거나 빈 화면 | 마지막 성공 데이터 + "N시간 전 기준" 명시 (stale 표시) |
| 12 | **사건 종료 조건** | 정의 없으면 무한히 후속이 붙음 | 4절 (7일 무활동 → closed) |
| 13 | **자산 식별 모호성** | "Gold"가 현물인지 GLD인지 GC=F인지, 티커 충돌(해외/국내 동일 티커) | `assets`에 `(source, source_symbol)` 매핑 테이블을 별도로 |
| 14 | **인사이트 3의 수집 정당성** | 증권사 리서치·유료 콘텐츠는 크롤링 금지인 경우가 많음 | 기획서 20장대로 RSS/공개 API가 있는 소스로만 시작. **2차 기능으로 미루는 것을 권장** |
| 15 | **데이터 백업/이전** | SQLite 파일 손상 시 전부 소실 | 주 1회 자동 사본 + 설정에 "데이터 내보내기" |

## 15. 구현 로드맵

각 단계는 **그 자체로 쓸 수 있는 상태**로 끝난다.

### Phase 0 — 파이프라인 검증 (UI 없음) ★ 여기가 진짜 리스크 구간
> 목표: **"뉴스 30개 → 사건 3개"가 실제로 되는가?** 이게 안 되면 나머지는 의미가 없다.
> 산출물: **버리는 프로토타입이 아니라 최종 수집기 그 자체** (0.5절 참조)

**만드는 것**

```
mystock collect  --asset NVDA        # 수집 → 파이프라인 → SQLite 기록 (스케줄러가 부를 진입점)
mystock brief    --window 7d         # DB 조회해서 사람이 읽을 형태로 출력
mystock cost                         # 누적 토큰/비용 리포트
mystock compare  --model opus5,haiku # 같은 입력으로 두 모델 결과 나란히
```

- TypeScript / Node, `better-sqlite3`
- 자산 1개(NVDA)로 시작 → 검증되면 2~3개로 확대
- 8절 스키마 중 `articles / events / event_articles / job_runs` 만 먼저
- 로컬 임베딩(`transformers.js` 다국어 모델)으로 Stage 2~3
- LLM 호출은 구조화 출력 + 토큰 사용량 전량 로깅

**2주간 매일 돌리며 눈으로 검증할 것** — 이게 Phase 0의 본체다

| 검증 질문 | 실패하면 |
|---|---|
